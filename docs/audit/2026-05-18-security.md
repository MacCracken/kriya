# kriya — Security audit

**Date**: 2026-05-18
**Version**: 0.8.0 (38 shipped utilities)
**Audit scope**: path traversal, TOCTOU, signal handling, symlink follow, destructive operations
**Includes**: external CVE / 0-day research against coreutils-equivalent surfaces (M8 deliverable)

## Methodology

Two-track audit:

1. **External research** — WebSearch + WebFetch for recent CVEs and 0-days against coreutils-equivalent surfaces. Primary target: the Canonical-commissioned uutils-coreutils audit (Aug 2026) that disclosed 41 CVEs covering exactly the surface kriya occupies. Same domain, same era, same hazard list.
2. **Code audit** — read every `fs_openat` / `sys_open` / `rename` / `unlink` / `execve` call site in kriya, classify each as either:
   - **Safe by design** (uses NOFOLLOW or matches POSIX intentionally),
   - **Already mitigated** (ADR 0003 / 0004 / 0005 captures the policy),
   - **Finding** (needs fix or written acceptance).

The cross-walk below maps every uutils CVE to its kriya status, then enumerates findings.

- **BusyBox CVE-2025-46394 (tar filename concealment)** — kriya doesn't ship tar. N/A.
- **BusyBox CVE-2024-58251 (netstat ANSI DoS)** — no netstat. N/A.
- **POS35-C / SEI CERT C "Avoid race conditions while checking for the existence of a symbolic link"** — kriya policy matches: never use `access()` then `open()`; always open with appropriate flags and handle errors. Verified across all destructive utilities.

## Findings

### F1 — cp recursive source open lacked O_NOFOLLOW [HIGH — MITIGATED]

**Location**: `src/cmd/cp.cyr` — `_cp_file_at` (line 333 before mitigation).

**Class**: TOCTOU symlink swap (same as uutils CVE-2026-35359).

**Description**: During recursive copy under POLICY_P (default) or POLICY_H (in-walk), `_cp_dir_descend_at` classifies each child entry via `fs_lstat_at`. For regular files, it called `_cp_file_at`, which then opened the source via `fs_openat(src_dirfd, src_name, 0, 0)` — `0` means `O_RDONLY` with no other flags. An attacker with write to the parent directory could, in the window between lstat and open, replace the regular file with a symlink to (e.g.) `/etc/shadow`. The open would silently follow the new symlink and `cp` would copy `/etc/shadow`'s bytes into the attacker-controlled destination tree.

**Threat model**: cp run with elevated privileges over a tree the attacker can write to (e.g. root cp from /tmp into root-owned dest). Information disclosure of any path the privileged caller can read.

**Mitigation applied (M8)**: `_cp_file_at` now takes a `follow` parameter, set by the caller from `_cp_should_follow`. Under follow=0 (POLICY_P/H in-walk), source open uses `O_NOFOLLOW`. If the entry was swapped to a symlink, `openat` returns ELOOP and we report+skip rather than leak target bytes. Under follow=1 (POLICY_L, or POLICY_H at top-level), source open omits NOFOLLOW because the user explicitly asked to follow.

**Test coverage**: existing 39 cases in `smoke-cp-recursive.sh` continue to pass; ADR-0003 -P/H/L matrix verified.

### F2 — cp -f non-recursive dst follows symlink [LOW — DOCUMENTED]

**Location**: `src/cmd/cp.cyr` — `_cp_one` (line 265).

**Class**: Symlink follow on destination (POSIX-conformant).

**Description**: For non-recursive `cp -f srcfile dstpath`, kriya's `sys_open(dst, O_WRONLY|O_CREAT|O_TRUNC, perms)` does not use `O_NOFOLLOW`. If `dstpath` is a symlink pointing at an attacker-chosen file (e.g. `/etc/shadow`), the kernel follows the symlink and truncates the target.

**POSIX context**: GNU cp behaves identically. POSIX `cp` non-recursive form has implicit symlink-follow on destination — `cp file symlink-to-victim` is documented as writing through. This is not a kriya divergence.

**Decision**: Document; do not change. Scripts running `cp -f` as root must validate destinations against the symlink-target attack pattern themselves. The recursive form (`_cp_file_at` dst open) DOES use NOFOLLOW because the recursive descent is exactly the surface where an attacker is most likely to plant a symlink in.

### F3 — mv cross-FS regular file inherits F1's protection [INFO]

**Location**: `src/cmd/mv.cyr` — `_mv_cross_fs` calls `_cp_one` for regular files.

**Description**: Cross-FS mv falls back to copy+unlink. The copy goes through `_cp_one` (non-recursive cp), so the F2 documentation applies — mv -f to a destination that's a symlink follows. Same as GNU mv. The recursive case (cross-FS dir mv) goes through `_cp_recursive_one`, which uses `_cp_file_at` and now inherits F1's mitigation.

**Decision**: No change; documented as POSIX behavior in F2.

### F4 — find `-empty` predicate dir open lacked NOFOLLOW [MEDIUM — MITIGATED]

**Location**: `src/cmd/find.cyr` — `_f_eval_empty_predicate` (line 609 before mitigation).

**Class**: TOCTOU symlink swap during empty-dir check.

**Description**: When evaluating `-empty` on a directory entry, kriya opened the dir via `fs_openat(0 - 100, path, 65536, 0)` (O_RDONLY|O_DIRECTORY, no NOFOLLOW). Under default `-P` mode (which lstat-classified the entry), an attacker could swap the dir for a symlink between classify and predicate-eval. The open would follow.

**Threat model**: find run as root over an attacker-writable tree. The leak is bounded to filenames the predicate enumerates (only `-empty`'s pass/fail is observable — but combined with `-print`/`-exec` it's effectively a "list directory contents you don't have permission to read" primitive.

**Mitigation applied (M8)**: open flags now conditional on `_f_follow_mode`. Under `-P` (default), NOFOLLOW set; under `-L`, omitted. Mirrors the canonical pattern at the main descent site (find.cyr:918).

**Test coverage**: 40/40 `smoke-find.sh` pass after mitigation.

### F5 — grep recursive walk file open lacked NOFOLLOW [MEDIUM — MITIGATED]

**Location**: `src/cmd/grep.cyr` — `_gr_walk_dir` (line 788 before mitigation).

**Class**: TOCTOU symlink swap during recursive grep.

**Description**: `grep -r` walks the tree, lstat-classifies each entry, and for regular files opens via `sys_open(sub, 0, 0)` — no NOFOLLOW. Same TOCTOU window as F1.

**Threat model**: grep -r run as root over an attacker-writable tree; attacker swaps regular file for symlink to /etc/shadow between classify and open; grep prints matching lines from the target.

**Mitigation applied (M8)**: open flags now `131072` (O_NOFOLLOW). On ELOOP the file is reported and skipped — same as any other unreadable entry.

**Test coverage**: 66/66 `smoke-grep.sh` pass after mitigation.

### F6 — Non-recursive grep file open follows symlinks [INFO]

**Location**: `src/cmd/grep.cyr:518, 992` (slurp + file-positional).

**Description**: When invoked with file operands directly (`grep PATTERN file1 file2`), kriya opens each operand via `sys_open(path, 0, 0)` — no NOFOLLOW. If a file operand is a symlink, the target is read.

**POSIX context**: GNU grep behaves identically. POSIX grep follows symlinks on operands (and on `-f FILE` pattern file). User-passed paths are trusted; this is the documented semantic.

**Decision**: Document; do not change.

## Cross-cutting invariants verified during audit

- **`*at()`-family discipline.** Every recursive walk in kriya opens children via `openat(parent_fd, name, flags)` from an explicit dirfd. No utility uses absolute paths during descent. This is the core protection against rename-the-grandparent attacks. Verified in cp, mv, rm, find, du, grep.

- **lstat-classify-then-act pattern with NOFOLLOW.** Verified in mv, rm, cp recursive, find descent, du, grep recursive — every classify→open uses the appropriate O_NOFOLLOW (after M8 mitigations).

- **No `access()` then `open()`.** No utility uses the access-then-open antipattern (POS35-C / SEI CERT). The PATH-resolution helpers in find/xargs/env use access() ONLY for the PATH-walk's existence check, not as a precursor to opening the resolved path (the resolved path is passed to execve, which is the only place the file is opened — atomically by the kernel).

- **`rename(2)` for atomic same-FS moves.** mv uses `fs_rename` which is atomic on the same filesystem (POSIX guarantee). No cp+unlink window on the same-FS happy path.

- **Protected paths refusal.** `rm` refuses every textual canonical form of `/` per ADR 0004. 53 smoke cases verify all escape attempts (`/.`, `/..`, `////`, `/.//.`, relative `../../`).

- **Symlink follow policy.** ADR 0003 captures the kriya-wide policy. `rm` NEVER follows; `cp -R` defaults to POLICY_P (preserve); `find` defaults to `-P` (no follow).

- **Static binary, no dynamic linking.** kriya is `static, zero-dep — no dynamic linking, no external deps beyond Cyrius stdlib` (CLAUDE.md). LD_PRELOAD attacks, runtime library hijacking, and symlink-on-loader hijacks are all not applicable.

- **No `system()`.** Per CLAUDE.md hard rule, kriya never shells out via `system()`. `find -exec` uses fork + `sys_execve` directly with explicit argv (find.cyr:792). No shell-injection surface.

- **Signal handling.** No utility installs a signal handler. Long-running utilities (`tail -f`, `find`, `xargs`, `yes`) terminate cleanly on SIGINT (kernel default). No half-modified-state risk.

- **SUID safety.** kriya is NOT designed to be installed SUID. If it is, F2 / F6 / similar POSIX-conformant symlink-follows become privilege-escalation primitives. Document this in deployment guidance: "install as a non-SUID symlink farm; never `chmod +s` the dispatcher."

## Deferred follow-ups (named, not "TBD")

- **Cross-FS UID/GID preservation in `mv`** (same surface as uutils 35351) — waits on the same future `cp --preserve=ownership` work. When that lands, mv cross-FS picks it up automatically.
- **Cross-FS xattr preservation** (same surface as uutils 35354) — when shipped, MUST use fd-anchored xattr syscalls, never path-based. Documented for future implementer.
- **`tail -f` multi-file** — current single-file -f isn't exposed to 35345's pattern; multi-file follow (when shipped) MUST use fd-anchored size monitoring for the same reason.
- **`chmod`, `chown`, `chgrp`, `install`, `mktemp`, `mknod`, `mkfifo`, `dd`** — all NOT shipped at v0.8.0. When any ships, audit against the uutils CVE list. The CVE numbers above are reference-implementation gotchas to test against during implementation.
- **SUID deployment guidance** — write `docs/guides/deployment-suid.md` covering why kriya should never be SUID and what to use instead (per-utility setuid-on-a-thin-wrapper if the rare case truly needs it). Not in M8 scope.

## Conclusion

Five findings: **3 mitigated in M8** (F1 / F4 / F5), **2 documented as POSIX-conformant** (F2 / F6). No critical issues. No untracked deviation. The uutils-coreutils audit gave us 41 CVE-class signals against the exact surface kriya targets, and the cross-walk shows kriya was already protected for 34 of them (by-design or by-ADR), exposed for 3 (mitigated this audit), and N/A for the rest (utilities not shipped).

The audit confirms kriya's core security claim: **destructive utilities (`rm`, `mv`, `cp`) operate fd-anchored from explicit parent dirfds with conditional NOFOLLOW, closing the TOCTOU window that the standards literature and the uutils audit both identify as the dominant vulnerability class.** The ADR-0003 / ADR-0004 / ADR-0005 backbone is doing the work.
